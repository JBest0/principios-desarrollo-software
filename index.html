Los cuatro pilares de la POO

Abstracción

Extraer lo importante de un objeto del mundo real y llevarlo a una clase.

Superhéroe: volar() y superFuerza()

Encapsulamiento

Proteger la información del objeto para que nadie la manipule sin autorización.

atributos privados, métodos públicos

Herencia

La clase hija hereda atributos y métodos de la clase padre.

Superheroe → Superman, IronMan

Polimorfismo

Objetos distintos, mismo método, distinta implementación.

ambos vuelan, de formas distintas

Interfaces y clientes

Interfaz = contratoel timón de un auto
interface Volador {
void volar();
}
class Superman implements Volador {
public void volar() { /* con poderes */ }
}
class IronMan implements Volador {
public void volar() { /* con un traje */ }
}

Interfaz: define el nombre del método y sus argumentos, pero no cómo se implementa.

Como el timón: cada fabricante usa su tecnología, pero todos cumplen el contrato de darle un timón al conductor.

Cliente: la parte del programa que usa una clase o interfaz (el conductor es cliente del timón).

Robert C. Martin, 2000 · Objetivo: bajo acoplamiento

S · Responsabilidad Única

✗ Malmuchas razones para cambiar
class Superheroe {
void volar() { ... }
void treparParedes() { ... }
void lanzarFuego() { ... }
}

Una sola clase con demasiadas habilidades: demasiadas razones para cambiar.

✓ Bien1 razón por clase
class Superheroe {
void realizarSuperHabilidades() { ... }
}
class Volar { ... }
class TreparParedes { ... }
class LanzarFuego { ... }

Una sola función; cada habilidad se delega a su propia clase.

O · Abierto / Cerrado

✗ Maleditar para extender
class Superheroe {
void realizarSuperHabilidades() {
volar();
}
void volar() { ... }
}

Agregar volar() obliga a editar la clase Superheroe.

✓ Bienextender sin modificar
interface Habilidad {
void usar();
}
class Volar implements Habilidad {
public void usar() { ... }
}
class Superheroe {
Superheroe(Habilidad h) { ... }
}
// Nueva habilidad: solo otra clase

Una interfaz y una clase por habilidad: se extiende sin tocar Superheroe.

L · Sustitución de Liskov

✗ Malel hijo agrega restricciones
class SuperheroeVolador extends Superheroe {
void volar() {
if (!tieneSuperpoderes)
throw new RuntimeException();
}
}
class IronMan extends SuperheroeVolador { }

La restricción excluye a Iron Man (vuela con un traje): ya no puede sustituir a Superman.

✓ Bienel hijo cumple el contrato
class SuperheroeVolador extends Superheroe {
void volar() { ... }
}
class Superman extends SuperheroeVolador { }
class IronMan extends SuperheroeVolador { }

Sin restricciones extra: Superman e Iron Man son intercambiables.

I · Segregación de Interfaces

✗ Malinterfaz demasiado grande
interface Habilidades {
void volar();
void treparMuros();
void lanzarFuego();
}
class Superman implements Habilidades {
public void volar() { ... }
public void treparMuros() { /* ??? */ }
public void lanzarFuego() { /* ??? */ }
}

Superman está obligado a trepar muros y lanzar fuego, habilidades que no tiene.

✓ Bieninterfaces pequeñas
interface Volador {
void volar();
}
interface TrepaMuros {
void treparMuros();
}
class Superman implements Volador {
public void volar() { ... }
}

Una interfaz por habilidad: cada superhéroe implementa solo las suyas.

L vs I · ¿en qué se diferencian?

L · LiskovI · Segregación
Pregunta¿El hijo cumple lo que promete el padre?¿La interfaz pide más de lo necesario?
El problema está enEl comportamiento del hijoEl tamaño de la interfaz
SíntomaEl hijo falla o cambia lo esperadoMétodos vacíos o con excepción

A menudo se arreglan con el mismo cambio, pero no miran el mismo problema.

D · Inversión de Dependencias

✗ Maldepende de clases concretas
class Avengers {
IronMan ironMan = new IronMan();
Capitan cap = new Capitan();
}
// ¿Agregar a Hulk? Editar Avengers

Avengers crea a sus miembros: agregar a Hulk obliga a modificarla (y viola O).

✓ Biendepende de un contrato
interface Avenger {
void atacar();
}
class Avengers {
List<Avenger> equipo;
Avengers(List<Avenger> e) { equipo = e; }
}
// Hulk: solo otra clase Avenger

Recibe los Avenger desde afuera (inyección de dependencias).

Estilos arquitectónicos

Monolito

Todo se construye y despliega como una unidad.

+ simple al inicio

− todo cambio redespliega todo

En capas

Presentación → lógica → datos.

+ separación clara

− sigue siendo una unidad

Hexagonal

Núcleo aislado por puertos y adaptadores.

+ núcleo testeable

− capa extra de abstracción

Microservicios

Servicios pequeños desplegados por separado.

+ escalan por separado

− complejidad operativa

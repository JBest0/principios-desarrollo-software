El problema: GestorPedidos


public class GestorPedidos {

    public double calcularTotal(Pedido pedido) {
        double total = 0;
        for (Item item : pedido.getItems())
            total += item.getPrecio() * item.getCantidad();
        if (pedido.getTipoCliente().equals("VIP")) {
            total *= 0.9;
        } else if (pedido.getTipoCliente().equals("MAYORISTA")) {
            total *= 0.85;
        }
        return total;
    }

    public void guardarEnBaseDeDatos(Pedido pedido) {
        System.out.println("Guardando pedido " + pedido.getId());
    }

    public void enviarConfirmacion(Pedido pedido) {
        System.out.println("Enviando confirmacion a " + pedido.getCliente());
    }
    // procesarPedido() llama a los tres...
}

Tres razones para cambiar en una sola clase → viola S · nuevo cliente = editar el if → viola O

Estilos arquitectónicos

Monolito

Todo se construye y despliega como una unidad.

+ simple al inicio

− todo cambio redespliega todo

En capas

Presentación → lógica → datos.

+ separación clara

− sigue siendo una unidad

Hexagonal

Núcleo aislado por puertos y adaptadores.

+ núcleo testeable

− capa extra de abstracción

Microservicios

Servicios pequeños desplegados por separado.

+ escalan por separado

− complejidad operativa
